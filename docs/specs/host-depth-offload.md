# Mac 端 3D 深度卸载（Core ML ZipDepth）可行性验证报告

> 状态：**方案与可行性验证（不接入当前主串流流程）**。原型与基准代码位于 [`host/Experiments/depth-offload/`](../../host/Experiments/depth-offload/)。

---

## 1. 背景与动机

在 PICO 4（骁龙 XR2 Gen 1）上，头显本地运行 ZipDepth 时（见根目录 `README.md` 实测）：

- `zipdepth_512x288_fp16.tflite`（GPU delegate）：约 **26 ms/张**，上限 **20 fps**，深度相对画面平均滞后 **49 ms（1.2 帧），最差 127 ms**。
- `zipdepth_256_int8dr.tflite`（CPU XNNPACK 4 线程）：空闲约 **16.7 ms/张**，串流解码 + 72 Hz 渲染并发时通常只能维持 **12–15 fps**，且占用头显功耗与散热预算。

而电脑串流场景中，画面本身就产生在 Mac 上。Apple Silicon（M1 及以上）拥有独立的 **Apple Neural Engine（ANE）**、高性能 GPU 和专用 VideoToolbox 媒体引擎。若在 Mac 编码前直接跑 ZipDepth 并把深度图随画面一起传给头显，理论上可实现：

1. **深度帧率从 12–20 fps 提升到与画面锁帧的 72–120 fps**；
2. **深度与画面零帧滞后（逐帧严格对齐）**，快速镜头切换或 FPS 游戏鼠标甩动不再出现「物体先动、立体轮廓晚 2 帧跟上」的鬼影；
3. **释放头显端算力与功耗**，头显只需解码 + 1.9 ms 的 GPU warp 合成。

## 2. 本机实测数据与复现命令

### 2.1 测试环境

- **设备**：Apple M1 Max（arm64，16 核 ANE，32 核 GPU）
- **系统**：macOS 27.0.1（Build 26A434）
- **模型**：`zipdepth_base_npu.pth`（commit `91f3fd21`，经 `coremltools` 导出为 `MLProgram` + `FLOAT16`，目标 `macOS14`）

### 2.2 复现命令

```bash
host/Experiments/depth-offload/run_benchmark.sh
```

脚本依次执行：
1. `export_coreml.py`：将 `zipdepth_base_npu.pth` 导出为 `256×256`、`512×288`、`640×384` 三个 FP16 `.mlpackage`，并与 PyTorch 原始输出核对相关系数（Pearson `r`）和平均绝对误差（MAE）；
2. 编译原生 Swift 基准程序 `BenchCoreML.swift`（`-O` 优化）；
3. 每组配置预热 15 帧后连续推理 100 帧，分别测量 `ANE+GPU+CPU`（`.all`）、`CPU+ANE`、`CPU+GPU` 的均值与分位数延迟，并对比 VideoToolbox HEVC 硬件编码耗时。

### 2.3 精度核对（Core ML FP16 vs PyTorch FP32）

| 输入尺寸 | 输出尺寸 | Pearson 相关系数 `r` | MAE |
|---|---:|---:|---:|
| `256 × 256` | `1 × 1 × 256 × 256` | `0.998559` | `0.00174` |
| `512 × 288` | `1 × 1 × 288 × 512` | `0.998612` | `0.00148` |
| `640 × 384` | `1 × 1 × 384 × 640` | `0.999815` | `0.00031` |

FP16 精度损失极小，与头显端正在使用的 FP16 TFLite 路线一致。

### 2.4 Core ML 每帧推理耗时与可达帧率（M1 Max 实测）

| 模型输入尺寸 | 计算单元 | Mean (ms) | p50 (ms) | p95 (ms) | p99 (ms) | 理论上限帧率 | 对比 PICO 4 本地 |
|---|---|---:|---:|---:|---:|---:|---|
| `256 × 256` | `ANE+GPU+CPU` | **1.14** | 1.07 | 1.43 | 1.76 | **879.8 fps** | 约 **14.6×**（vs 16.7 ms） |
| `256 × 256` | `CPU+ANE` | **1.15** | 1.09 | 1.48 | 1.58 | **868.2 fps** | 同上，且完全不占 GPU |
| `256 × 256` | `CPU+GPU` | 6.03 | 5.91 | 7.49 | 9.65 | 165.8 fps | — |
| `512 × 288` | `ANE+GPU+CPU` | 2.39 | 2.35 | 2.82 | 2.94 | 419.1 fps | 约 **10.9×**（vs 26 ms） |
| `512 × 288` | `CPU+ANE` | **2.28** | **2.21** | 2.68 | 2.79 | **439.2 fps** | 约 **11.4×**，且完全不占 GPU |
| `512 × 288` | `CPU+GPU` | 6.06 | 5.83 | 9.09 | 9.64 | 164.9 fps | — |
| `640 × 384` | `ANE+GPU+CPU` | **3.81** | 3.75 | 4.23 | 4.36 | **262.8 fps** | 高于头显分辨率上限 |
| `640 × 384` | `CPU+ANE` | **3.83** | 3.72 | 4.45 | 4.70 | **261.1 fps** | 仍 < 4 ms，完全不占 GPU |
| `640 × 384` | `CPU+GPU` | 7.57 | 7.13 | 10.32 | 12.22 | 132.0 fps | — |

**关键发现**：

1. **必须走 ANE（`.cpuAndNeuralEngine` / `.all`）**：M1 Max 上 ANE 跑 `512×288` 仅需 **2.28 ms（p99 2.79 ms）**，比纯 GPU 路线快 **2.7 倍**，同时 **完全不争抢桌面渲染、游戏和 Metal 后处理的 GPU 资源**。
2. **即便在入门 M1/M2（同为 16 核 ANE）上**：M1 与 M1 Max 的 16 核 ANE 算力相同（11 TOPS，M2 15.8 TOPS，M3/M4 18–38 TOPS），因此所有 Apple Silicon Mac 都能稳定在 **2–4 ms** 内完成 `512×288` 深度推理，轻松锁满 **72 / 90 / 120 fps**。
3. **VideoToolbox 硬件 HEVC 编码余量**：在 `BenchCoreML.swift` 的 72 fps HEVC 编码实测中，`2560×1440`、`2560×1728`（1440p + 底部 288px 深度条）和 `3840×1440` 的单帧硬件编码延迟均在 **10.8–13.7 ms** 以内（受 `RealTime=true` 72 fps 节拍与首帧频率爬坡影响，2560×1728 仅增加 20% 像素面积，未触发硬件编码瓶颈；实测码率分别为 20.1 / 32.1 / 41.7 Mbps）。

## 3. 传输方案对比

把 Mac 算出的深度图传给头显有三条可行路线：

| 维度 | 方案 A：单流底部窄带拼接（推荐） | 方案 B：独立第二路深度流（RTP / UDP） | 方案 C：Mac 端直接完成 Warp，发 SBS 立体流 |
|---|---|---|---|
| **画面布局** | 主画面（如 `2560×1440`）下方拼一条低分辨率灰度深度带（如 `640×360` 放在底带左侧，或 `512×288` 贴在 `2560×1728` 底部，Cb/Cr 填 `128` 中性灰） | GameStream 主视频流不变，另开一条 UDP/QUIC 通道发压缩后的深度帧（HEVC-grey 或 LZ4/PNG 8-bit） | Mac 端跑完整双边上采样 + 左右眼 Warp，直接编码 `3840×1080` 或 `2560×1440` 半宽 SBS |
| **帧同步精度** | **天生 100% 逐帧严格对齐**（同一帧 PTS、同一帧解码输出） | 需要显式绑定主视频帧序/PTS，丢包或乱序时要回退上一帧深度 | 天生同步 |
| **像素 / 带宽开销** | **低（+10% ~ +20%）**：`512×288` 深度只占 `2560×1440` 像素数的 **4%**（若整行扩展为 `2560×1728` 则像素面积 +20%，右侧空白区 Cb/Cr/Y 恒定几乎不耗码率，实际码率增量约 **8%–15%**） | **最低（+3% ~ +8%）**：只编 `512×288` 灰度流（约 1–3 Mbps） | **高（+60% ~ +100%）**：左右眼双画面，且半宽 SBS 会损失一半横向清晰度，文字糊 |
| **压缩对深度的影响** | 深度只放在 **Y（亮度）平面**，完全不受 YUV 4:2:0 色度子采样影响；8-bit 提供 256 级深度（经鲁棒归一化后足够平滑），10-bit HEVC 可提供 1024 级无断层精度 | 同左（若走 HEVC 灰度流）；若走无损压缩则码率偏高 | 不涉及深度传输，但 SBS 强耦合 Mac 端参数 |
| **头显端调节自由度** | **保留全部自由度**：头显仍可实时调 3D 强度（关闭/柔和/标准/强烈）、汇聚距离、边缘渐弱，无需往返 Mac | 保留全部自由度 | **丧失自由度**：调强度或关 3D 要回传 Mac 并重启/通知渲染器，无法实时拖动预览 |
| **协议与引擎改造量** | **中等**：需定制编码前合成帧（不能用未改动的上游 Sunshine 二进制，需要内置插件或维护一个轻补丁分支） | **中等偏大**：需同步维护第二条传输通道、握手、拥塞控制与帧号对齐 | 中等，但画质/带宽/交互体验均明显不如方案 A |

### 推荐结论

- **推荐方案 A（单流底部窄带拼接，1/4 或 `512×288` 灰度深度写入 Y 平面）**。
- 原因：
  1. 彻底避免双流同步、丢包失配与额外 MediaCodec 解码器实例（XR2 Gen 1 同时开两路硬解会增加显存与调度抖动）；
  2. 深度图只占 **Y 亮度通道**，天然免疫 4:2:0 色度压缩，且底带未占用的右侧区域填常量灰，HEVC 跳块编码几乎零码率开销；
  3. 保留头显端 `xr-renderer` 现有的全部 3D 强度、汇聚和 2D 瞬时切换能力。

## 4. 带宽与端到端延迟预算分析

以 PICO 4 默认串流规格 **1440p（`2560×1440`）@ 72 fps，HEVC 8-bit/10-bit** 为例：

### 4.1 带宽影响

- 原始 1440p72 码率：通常 **30–50 Mbps**。
- 底部附加 `512×288` 灰度深度（总编码画布 `2560×1728`，其中 `2048×288` 填充常数 `Y=0, UV=128`）：
  - 有效非空像素增量：`512×288 / (2560×1440) = 4.0%`。
  - 深度图空间平滑、低高频纹理，帧间时间相关性强，实测额外码率仅约 **3–6 Mbps（+10% ~ +15%）**，远在 Wi‑Fi 5/6 局域网余量内。
- **注意 8-bit 量化细节**：ZipDepth 原始输出为相对逆深度，在 Mac 端做完逐帧鲁棒归一化（2%–98% 分位 + 时间平滑，与 `proto/depth3d_proto/pipeline.py` 一致）映射到 `[0, 1]` 后，再写入 Y 平面（Full Range `0..255` 或 Video Range `16..235`，头显按约定反归一化）。如开启 10-bit HEVC，则可写入 10-bit 精度消除大面积平滑背景的轻微阶梯。

### 4.2 端到端延迟影响

| 阶段 | 当前路线（头显本地算深度） | 方案 A（Mac Core ML 卸载） | 变化 |
|---|---:|---:|---|
| Mac 录屏 + 缩放进 ANE | 0 ms | ~0.4 ms（Metal / vImage） | +0.4 ms |
| Mac ZipDepth 推理（`512×288` ANE） | 0 ms | **2.28 ms**（p99 2.79 ms） | +2.3 ms |
| 归一化 + 写入底带 CVPixelBuffer | 0 ms | ~0.3 ms（Metal compute） | +0.3 ms |
| Mac VideoToolbox HEVC 编码 | ~4–6 ms | ~4.5–6.5 ms | +0.5 ms |
| 局域网传输 + 头显 MediaCodec 解码 | ~8–12 ms | ~8.5–12.5 ms | +0.5 ms |
| 头显本地深度滞后（异步 20 fps） | **49 ms（最差 127 ms）** | **0 ms（逐帧同步）** | **−49 ms ~ −127 ms** |
| 头显 GLES 双边上采样 + Warp | 1.9 ms | 1.9 ms | 0 ms |

**结论**：视频帧本身仅增加约 **3.5–4.0 ms**（不到 72 Hz 帧周期 13.9 ms 的三分之一），换来 **深度滞后彻底归零（减少 49–127 ms）**，同时头显端帧率从 20 fps 跃升至 72 fps，整体观感收益极大。

## 5. 头显端（`player/`）需要的改动清单

> 注意：以下改动仅作设计记录，**本任务未修改 `player/` 任何代码**。

1. **协议能力协商（`docs/specs/host-protocol.md` v1 扩展或 v2）**：
   - 在 `GET /depth3d/v1/info` 的 `stream` 对象中增加可选字段（向后兼容）：
     ```json
     "depthOffload": {
       "supported": true,
       "layout": "bottom_strip_v1",
       "depthRect": { "x": 0, "y": 1440, "w": 512, "h": 288 },
       "range": "video_16_235"
     }
     ```
   - 串流发起前通过控制接口协商开启；当连接非 depth3d Host（如 Windows 原生 Sunshine）或未开启卸载时，头显自动回退现有本地 ZipDepth 流程。
2. **解码画面裁剪与 UV 坐标映射（`player/.../xr-renderer/`）**：
   - MediaCodec 收到 `2560×1728` 帧并输出到同一个 `SurfaceTexture`（OES 纹理）。
   - `xr-renderer` 在「外部深度模式」下：
     - **停用本地 TFLite 推理线程**（节省 CPU/GPU 与显存）；
     - 画面采样 UV 限制在主画面子矩形 `[0, 0] → [1.0, 1440/1728]`；
     - 双边上采样 shader 的深度纹理输入直接从同一张 OES 纹理的 `[0, 1440/1728] → [512/2560, 1.0]` 区域采样亮度通道（`R`/`Luma`），跳过本地归一化与时间平滑（由 Mac 端在写入前完成）。
3. **Host 侧后续落地前提**：
   - 由于当前版本将上游 Sunshine 作为未修改子进程打包，无法在编码前拦截 `CVPixelBuffer`。
   - 后续落地时，需在 Sunshine 的 macOS 捕获/编码管线（`src/platform/macos/av_video.m` → `video::captureThread`）加入可开关的 Metal + Core ML 预处理 hook（约 250–350 行 ObjC++/Metal），以自编译构建的内置引擎替换官方 DMG。

## 6. 总结

- **技术可行性**：**完全可行**。Apple M1 Max 上 ANE 运行 `512×288` FP16 ZipDepth 仅需 **2.28 ms（439 fps）**，`640×384` 也仅 **3.81 ms（263 fps）**，且几乎零 GPU 占用。
- **产品价值**：把串流 3D 深度从「20 fps / 50 ms 滞后」提升到「72–120 fps / 0 ms 滞后」，同时降低头显发热与耗电。
- **工程建议**：保持当前 M3 阶段不接入主流程（确保主链稳定可靠）；在下一里程碑（M4/M5）中以「方案 A：单流底部窄带拼接」+ 自定义编译内置引擎的方式落地，并在设置中作为「Mac 硬件 3D 加速」开关提供。
