# 产品级标准（所有任务都要满足）

depth3d 是要发布的产品，不是演示。每个任务交付时逐条自查，做不到的写进交付说明，不要悄悄跳过。

## 用户看到的
- 界面只照 `design-opus/ux-spec.md` 和 `design-opus/mockups/`。设计稿没覆盖的状态，按规范里的原则补，并在交付说明里列出来。
- 每个页面都有：加载、空、出错、无网络四种状态。出错文案说清楚「发生了什么、用户下一步做什么」，不出现异常类名、错误码、英文技术词。
- 全部界面文字是简体中文，放进资源文件（Android `strings.xml` / macOS String Catalog），不写死在代码里。不出现 Moonlight、Sunshine、MoonlightXR 等上游名字和图标（开源许可页除外）。
- 头显里不要求打字：能自动发现的自动发现，要输入的只用数字 PIN 或手机扫码。
- 任何操作 100 ms 内有反馈；超过 1 s 的有进度提示；能取消的都能取消。

## 工程
- 不留 TODO 占位、假数据、写死的地址和密码、调试用入口。
- 协议、状态机、解析等纯逻辑必须有单元测试，并在交付前跑通。
- 生命周期干净：页面退出时线程、服务、socket、解码器、锁都释放；旋转、休眠唤醒、Wi‑Fi 切换、对端突然断开都不崩溃、不卡死。
- 日志用统一前缀 `depth3d:`，不打印密码、密钥、PIN。
- 第三方代码：许可必须与 GPLv3 兼容，版本、来源、许可登记在 README 的表里。
- 不改和任务无关的文件；不动 `player/app/src/main/jni/xr-renderer/`，除非任务明确要求。

## 交付
- 一个任务一个分支，提交说明用英文，不要 push。
- 最后的回复用中文：分支和 commit、做了什么、和设计稿不一致的地方及原因、验证过什么（附命令和结果）、没验证的、已知风险、上机后怎么测。
